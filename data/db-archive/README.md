# radar.db, split for GitHub

`data/radar.db` is about 126 MB. GitHub rejects any single file over 100 MB, so
the database lives here instead as a **split zip archive** — one logical zip cut
into numbered parts, none larger than 25 MB.

| File | What it is |
| --- | --- |
| `radar-db.z01`, `radar-db.z02`, … | the leading parts |
| `radar-db.zip` | the **last** part, and the one that carries the central directory |
| `SHA256SUMS` | checksums for every part, plus the `radar.db` they rebuild |

The `.zip` is the final segment, not the whole archive — that is how Info-ZIP
names split sets, and it means the parts are useless individually.

## Restoring

```sh
./scripts/db-archive-restore.sh            # writes data/radar.db
./scripts/db-archive-restore.sh --force    # replaces an existing one
```

The script verifies the part checksums, rejoins, unzips, runs
`pragma integrity_check` on the result, and clears any stale `-wal`/`-shm` left
by the database it replaces.

By hand, the rejoin step is the one that catches people out — `unzip` cannot
read a split archive directly and will only report a missing disk:

```sh
cd data/db-archive
zip -s 0 radar-db.zip --out /tmp/joined.zip   # rejoin first
unzip /tmp/joined.zip -d ../                  # then extract
```

## Refreshing

```sh
./scripts/db-archive-pack.sh
```

Run it after a pipeline refresh when the committed copy should catch up. It
snapshots with `VACUUM INTO` rather than copying the file, because the live
database runs in WAL mode and a plain copy can miss committed pages still in
`radar.db-wal`.

## What this is not

A source of truth. The database is regenerated by every pipeline run, and the
deployed instance is seeded from the package `scripts/deploy-azure.sh` builds,
not from this directory. Each refresh also adds a fresh ~30 MB of binary to Git
history, which never shrinks — if that becomes a problem, the answer is Git LFS
or a release asset, not smaller parts.
